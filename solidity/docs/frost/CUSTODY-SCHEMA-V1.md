# Shared qualified-custody schema (local C-05 component)

C-05 owns `FrostCustody` and the data-only `IFrostFundingProof` types. The parent owns the Bridge storage location, FrostDeposits storage, funding-proof handler and admission API. C-04 consumes this common custody schema after rebasing; it owns reservation and proof-backed redemption/cancellation transitions. This schema neither depends on the unpublished C-04 ledger nor changes the existing registry FrostWallet type/encoding.

`FrostCustody.Storage.wallets[bytes32 fullWalletId]` stores `Wallet {uint64 generation; uint64 stateVersion; uint64 value; bytes32 mainOutpoint; bytes32 activeReservation; uint64 cancellationExposure;}`. `outputs[bytes32 outpointKey]` stores `Output {bytes32 walletId; uint64 value; bool spent;}`. These are storage structs, not additions to the existing wallet ABI. The Bridge owner must select/layout the storage slot; this library invents no delegatecall slot.

`outpointKey(rawTxHash,uint32 outputIndex)` is Keccak256 of exactly the 32 raw Bitcoin hash bytes followed by four big-endian packed Solidity uint32 bytes. No display-order hash reversal or wire-order index reversal. All consumers must use this helper.

`credit(Storage storage,bytes32 walletId,uint64 generation,bytes32 rawTxHash,uint32 outputIndex,uint64 value)` is internal and returns the outpoint key. The caller must first authenticate the full wallet ID and use its current custody intent counter, canonical funding output script/value and SPV inclusion. A nonzero ID is only a structural check, not proof of registry membership. This library cannot verify those facts. Generation is the uint64 C04 intent counter, initially zero; registry readiness32 is separate. Raw hash bytes are already verified by the proof consumer.

Credit requires a positive value at most 21 million BTC and an aggregate wallet value within that monetary cap. It requires no previously recognized output at that outpoint, including spent outputs or another wallet's output. Proven additional deposits are accepted during an active reservation, subject to an already initialized version and nonempty main outpoint. Never erase spent output tombstones. First credit initializes stateVersion to 1 with caller-supplied current intent counter 0; subsequent credits require the same generation. Outside a reservation they increment stateVersion with checked arithmetic; during a reservation they preserve the captured stateVersion. Other owner-controlled custody/availability mutations must advance stateVersion and must not reset it to zero. C04 reservation admission advances the intent counter through its authorized owner transition; credit never advances it. Never compare it with the registry uint32 readiness generation. Subsequent sweep credits pass custody.wallets[walletId].generation, not the registry wallet generation.

Credit sets mainOutpoint only if empty. Additional recognized outputs increase total value without replacing an existing main outpoint. Changing/clearing a main outpoint, marking an output spent, adjusting value/exposure and preserving reservation/escrow consistency require the relevant canonical spend-proof consumer. Merely marking an output spent does not authorize re-crediting its old outpoint. Cancellation exposure is reserved schema data; credit does not change or validate its semantics.

`IFrostFundingProof.FundingProof {BitcoinTx.Info transaction; BitcoinTx.Proof proof; uint32 outputIndex;}` reuses the existing transaction/SPV byte schema. It is untrusted transport data, not a proof acceptance claim. It exposes no callable interface or public credit setter. Parent admission must bind receipt terms, selected output and custody identity. Test-only FrostCustodyFixture state setters are outside production.

This is a local component only, with focused unit tests. No funded-state, custody qualification, canonical provider, deployment, or milestone exit is established.

## Additive deposits during an admitted plan

While activeReservation is nonzero, credit changes only wallet.value and the new output record. It preserves generation, stateVersion, mainOutpoint, activeReservation and cancellationExposure. It cannot initialize malformed active state, overwrite any captured output or mark anything spent. No main-replacement/consumption helper exists here: a non-settlement owner path must reject main replacement or captured-input consumption while a reservation is active. The canonical payment/cancellation settlement is the authorized exception and must validate the exact active ID and proof before consuming its captured inputs.

This version exception is safe only if the admitted plan durably captures the exact ordered recognized inputs/values and transaction snapshot, and settlement uses that captured list rather than enumerating current wallet outputs or assuming wallet.value equals captured input value. Each captured record must still match wallet ID/value and be unspent. Settlement must subtract consumed captured values and add verified change; it must not assign wallet.value = change, which would erase later deposits. Cancellation must follow the same accounting for its actual captured conflict inputs. New deposits cannot be silently appended to an existing signed transaction or certificate. Other availability changes must remain blocked or invalidate authorization according to owner policy.

The current C-04 draft stores intent.inputs and subtracts each captured output value in settlement; its own custody schema has not yet been rebased onto this library. That source observation is compatibility evidence, not a composed runtime proof. Funding reveal must validate every deposit proof and avoid an outer blanket reservation rejection. The local tests prove field/output preservation and guards; they do not prove parent SPV acceptance, settlement, provider finality or admission integration.
